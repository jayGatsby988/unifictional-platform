# Scan photo analysis admission

The new `/api/native/finishes` endpoint reserves every paid model call before it starts. Hosted deployments need server-only `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` credentials for an existing Upstash Redis database with scripting and write access. The URL must be HTTPS, without user info, a query, or a path. Set `SCAN_FINISH_ADMISSION_NAMESPACE` to one stable application/environment name (letters, digits, `_` and `-`, up to 80 characters). All production instances, domains and redeployments serving the same budget must use the same database and namespace. Credentials must never have a `NEXT_PUBLIC_` prefix or enter client JavaScript. No database, account or paid service was provisioned as part of this change.

Without this configuration, hosted or production requests return `503` before contacting the AI provider. Redis errors, timeouts, malformed responses and uncertain writes also fail closed. Changing the namespace or deleting its keys resets its counters, so neither belongs in routine deployment scripts. This is a request budget for this endpoint, not a dollar budget or authorization system; other pre-existing AI routes are outside this guard.

The fixed limits are 100 admitted calls per UTC day for the entire application, 20 per client per UTC day, 6 per client per UTC hour, 3 concurrent globally and 1 concurrent per client. Each call still has the endpoint's existing bounds: at most 3 JPEG images, 1 MiB each, 2048 pixels per edge, a 4 MiB request, 7000 output tokens, no provider retries and a 150-second provider timeout. Fixed windows can admit another window's allowance immediately after the boundary. The total paid cost depends on the configured model and image/token usage. Budget exhaustion returns `429` with `Retry-After`.

One atomic Redis `EVAL` checks and reserves all counters and concurrency leases. Redis server time defines the windows; isolates do not supply independent clocks. All keys use the same Redis hash tag. A lease expires after 210 seconds, longer than the route's 180-second maximum duration. Successful, failed and cancelled model calls all release their own lease in `finally`; cumulative counters are never refunded, avoiding unlimited retries during provider errors. A lost release can temporarily consume capacity until expiry. An uncertain reservation is not retried and cannot trigger a provider call. Admission and release each have a 2.5-second transport timeout.

On Vercel the limiter uses the platform's `x-vercel-forwarded-for` header, hashes the identity with a server-only HMAC key, and groups IPv6 clients by `/64`. Redis keys contain no raw IP addresses or photos. On other hosting platforms, or when the platform IP is missing/invalid, clients conservatively share one client bucket; a trusted server-side identity adapter is required for distinct clients there. Request `Origin`, browser cookies and arbitrary forwarded headers are not authentication. IP limits cannot identify people, and users sharing a network also share a client budget. The global cap remains shared even when an attacker rotates addresses.

Only non-production, non-Vercel development on a loopback request URL can use the bounded in-memory fallback. It shares one client budget and keeps three counters plus one expiring lease. It is intended for local development and does not claim distributed protection. A local `next start` production build also requires Redis.

Verification: `scripts/check-scan-finish-admission.ts` covers configuration failures, malformed Redis results, concurrency, cumulative usage, cancellation, release failures and private key handling without a provider. Set `REDIS_TEST_CLI` and `REDIS_TEST_SOCKET` to an isolated local Redis instance to execute the actual Lua and cross-instance budget tests. `scripts/check-scan-finish-api.ts` uses an offline provider double and verifies HTTP admission behavior; it neither uploads photos nor makes paid requests.

The implementation follows [Upstash's REST command and authentication contract](https://upstash.com/docs/redis/features/restapi), [Redis's atomic script execution contract](https://redis.io/docs/latest/develop/programmability/eval-intro/) and [Vercel's documented request IP headers](https://vercel.com/docs/headers/request-headers#x-vercel-forwarded-for). Provisioning/configuring Redis and checking it in the deployed environment remain deployment prerequisites.
